slate
Workbench Quickstart What it does GitHub

Rows, indexes and a planner on top of object storage.

slate is a record layer: it turns an ordered key-value store into tables with secondary indexes, a cost-based query planner, joins, aggregates, and row-level security that is compiled into the scan rather than checked around it.

One head node speaks gRPC. Clients for Python, Go and TypeScript speak to it. The workbench runs the same kernel in your browser over 100,000 real New York taxi trips, with no server at all.

Quickstart

Start a head node from a TOML file, then talk to it. Every client holds its own copy of the schema and the server checks it on each request, so a declaration that disagrees with the catalog is refused rather than answered with the wrong column. 

from slate import Client, Column, Identity, Query, Table, ValueType, desc, u64

BOOKS = Table("books", [
    Column("id",        ValueType.U64),
    Column("author_id", ValueType.U64),
    Column("title",     ValueType.STR),
    Column("year",      ValueType.I64),
], primary_key=["id"])

with Client("127.0.0.1:7421", identity=Identity("u64:1", roles=["app"])) as client:
    session = client.session()
    session.insert(BOOKS, [[u64(10), u64(1), "A Wizard of Earthsea", 1968]])

    query = Query(BOOKS)
    query.where(query.c.year.ge(1960)).sort(desc(query.c.year)).limit(20)
    for row in session.query(query):
        print(row)

What it does

Rows on a KV store

An order-preserving tuple codec puts rows and secondary index entries in one keyspace. Index maintenance is atomic with the write.

A planner that costs

Table scans, index scans, point gets, ranges from IN lists and LIKE prefixes, covering scans that never touch a row, and histograms for range selectivity.

Joins and aggregates

Hash and index nested-loop, cost-chosen, all four join types, chains of three or more tables, grouped joins and grouped chains, ordered and limited over groups, and HAVING to filter them.

A grouping with no keys is one group over every row, which is what SELECT count(*) FROM trips means. The kernel had always answered it; only the browser's SQL front end refused, and that refusal is gone. Try it from “The whole table, in one row”.

Computed columns

hour(), day_of_week(), year() and the rest are evaluated per row and group, sort and filter like any column, on a single table or on a join. There is no date type: a timestamp is seconds since the epoch in an integer column.

On a join, every position is resolved in the joined row: the group key, the computed column and the aggregates may each read either table, and a qualified name like zones.id picks its side. So SELECT hour(pickup_time), avg(fare) … FROM trips JOIN zones works, where a key on one side and an aggregate on the other used to be the only shape available. An unqualified name that both tables have resolves to the left one and says so above the results, rather than choosing in silence.

A grouped join can be ordered — ORDER BY count(*) DESC — and the ordering is over the groups: a group is its key followed by its aggregates. An ungrouped join cannot be ordered at all, and says why: the kernel orders groups, not joined rows.

They read UTC unless given a second argument: a fixed offset, hour(pickup_time, '-05:00'), or a named zone, hour(pickup_time, 'America/New_York'). A name is resolved against a transition table built from IANA's tzdata — a few kilobytes of sorted integers for a curated list of zones, not the whole database — so daylight saving is looked up at each row's instant rather than guessed at. A zone outside the list is refused, and the refusal names the ones that are in it. The taxi sample in the workbench is New York wall clock already, which is why its quietest hour is 04:00 and not 09:00.

Relationships, loaded not lazy

#[record(has_many(Book, foreign = author_id))] declares one, and load_related fetches every parent's children in one read — measured at 1 scan where the per-parent loop it replaces takes 3. There is deliberately no lazy accessor: the feature an ORM is judged on and the N+1 it is blamed for are the same feature, because an accessor cannot tell whether it is being called once or ten thousand times.

Columns are named by field ident, not by string, so a typo is a compile error on both sides rather than a panic on first use.

Pages that do not shift

OFFSET reads and discards every row it skips, and counts rows — so a row deleted between two pages makes the reader silently miss one. A cursor is the last row's primary key and narrows the scan range instead: page 99 of 100 read 5 key-value pairs against the offset version's 495, and the deleted-row case is asserted both ways round.

page_records returns the rows and the cursor for the next page, so a caller never names a key column. A sorted query or a grouped read is refused rather than paged wrongly.

Exact decimals

A hundred rows of ten cents sum to exactly $10.00; the same rows as f64 give 9.99999999999998. Both are asserted, because a test that only showed the right answer would not establish there was anything to fix.

The scale lives on the column, so a decimal is an integer count of the smallest unit: it encodes as an integer, the ordering is the integer ordering, and SUM is exact. The cost is that a value cannot print itself — rendering needs the column.

Migrations, before the socket opens

Adding an index to a populated table used to make queries through it return nothing — no error, rows still on disk, and intermittently, depending on whether the index covered the query. Schema state now lives in its own keyspace, and the daemon reconciles before it binds its listener: a node that binds first accepts a connection and answers it wrongly.

[schema] migrate_on_start = false makes it verify and refuse to start instead, which is not the same as skipping.

Conditional writes

The store detects two writers overlapping in time. The common failure is the other one: read a row, decide, write it in a later transaction while somebody else wrote it in between. Nothing overlaps, so nothing is detected, and an edit is silently lost. replace_record(&previous, &next) writes only if the stored row still equals what was read.

Security in the kernel

RBAC and row policies are compiled into the predicate the executor evaluates and the bounds it scans — not checked by a wrapper a caller could route around.

One writer, many readers

A lease-fenced writer and read replicas, with read tokens so a session never reads its own writes backwards.

Three clients

Python, Go and TypeScript, tested against a real head node and against each other — one contract, three SDKs, identical answers.

How it is built

The interesting part of this project is not the feature list, it is the evidence. Most of what is here exists because a test found it.

  • Oracles, not examples. Every plan agrees with a full scan. Every join algorithm agrees with every other. A grouped join agrees with folding the join by hand. An n-way chain agrees with nested two-way joins.
  • Mutation testing. Changes are checked by breaking them and requiring a named test to fail. Several tests exist only because a mutation survived — and several of those revealed a test whose assertion the bug also satisfied.
  • Crash and fault injection. Torn writes, object-store failures, overlapping writers across a lease change, and a restart suite over the S3 path.
  • An adversarial security review, with each finding either fixed and pinned by a probe, or closed as inherent with the claim it contradicted narrowed to the truth.
  • A ledger. Every change carries an entry saying why it exists, what it was weighed against, and where it stops. A pre-commit hook refuses the commit otherwise.

What it is not

Not production-proven. Nothing runs this in anger. The correctness work is real and the operational track record is zero.

No SQL. Queries are built from typed client APIs. There is no parser and no plan for one.

No in-place promotion of a read replica to writer — promotion is a restart. No multi-writer. No cross-shard transactions, because there is no sharding.

The repository's README keeps a list of what is not built, and it is kept honest: an item is removed when it is built, or withdrawn in writing with the reasoning that retired it.

See it working

The explorer is an interactive demo: one database, three SDKs, and a switch that swaps which client library serves the request. A second switch changes who the database thinks is asking, so a row policy visibly takes rows away and a role without the right grant is refused — none of it enforced by the demo.

Five things to know first.

The client APIs are small, and they make more sense once these are clear. Everything deeper lives in the design notes at the bottom.

1 — Columns are ordinals, not names

Every reference a client builds is a column's position. The wire carries positions, so a client that accepted names would have to hold a second copy of the schema to resolve them — and that copy can disagree with the server's.

The clients hold a schema anyway, for a different reason: to check it. Every request carries a fingerprint of the table as the client understands it, and the server refuses a declaration that disagrees rather than answering with the wrong column. Declaring your columns in the wrong order is caught on the first request, not silently returned.

2 — A u64 and an i64 are different values

The tuple codec orders values by type first, then by value. So u64(7) and i64(7) sort to different places and are different keys. A client that guessed a type from a language-native integer would write rows that could not be found again.

That is why every client makes you say which one you mean — u64(7) in Python, slate.Uint(7) in Go, uint(7n) in TypeScript — and why the TypeScript client refuses number for 64-bit integers entirely: above 2^53 a JavaScript number is not the integer you typed, and a primary key is where that shows up latest.

3 — The head node does not authenticate

In trusted-header mode the node reads three headers — principal, tenant, roles — and believes them. It is correct only behind a proxy that sets those headers itself and strips any the client sent.

There is no default: a configuration with no [auth] section is refused at startup rather than falling back to something. A repeated identity header is refused too, rather than resolved, because the server cannot tell whether the proxy in front of it appends or replaces.

What the node does enforce is authorisation. RBAC grants and row policies are compiled into the predicate the executor evaluates and the key bounds it scans, inside the kernel, on every access path — including index-only scans, aggregates and joins. There is no unauthenticated door, because every read and write takes a security context.

One consequence worth knowing: EXPLAIN is its own action and a blanket data grant deliberately excludes it. A plan is costed against statistics describing rows a policy may hide, so a caller who can vary a literal and watch the estimate move can recover values they cannot read.

4 — Sessions keep your reads from going backwards

Reads can be served by replicas, which lag. A session carries a watermark: it remembers the furthest point it has read or written, and sends that as a floor on later reads. Without it, a read after a write can be served by a node that has not caught up — correct, and surprising.

Every client turns this on by default and spells the opt-out at length (sessionWithoutMonotonicReads), so choosing the cheaper, surprising behaviour is deliberate.

5 — Errors carry a kind, and one is deliberately not retryable

Every client maps failures to the same closed set of kinds. Three are worth knowing:

  • not-leader is retryable elsewhere, and carries the node to try. It is distinguished from a plain outage because the remedy differs.
  • unknown-outcome is not retryable, on purpose. The write may have landed, and retrying is how one write becomes two.
  • deadline-exceeded has the same ambiguity as the above, and is treated the same way.
