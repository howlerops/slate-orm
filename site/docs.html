Five things to know first.

The client APIs are small, and they make more sense once these are clear. Everything deeper lives in the repository's design notes, linked at the bottom — this page is what you need before reading them.

1 — Columns are ordinals, not names

Every reference a client builds is a column's position. The wire carries positions, so a client that accepted names would have to hold a second copy of the schema to resolve them — and that copy can disagree with the server's.

The clients hold a schema anyway, for a different reason: to check it. Every request carries a fingerprint of the table as the client understands it, and the server refuses a declaration that disagrees rather than answering with the wrong column. Declaring your columns in the wrong order is caught on the first request, not silently returned.

2 — A u64 and an i64 are different values

The tuple codec orders values by type first, then by value. So u64(7) and i64(7) sort to different places and are different keys. A client that guessed a type from a language-native integer would write rows that could not be found again.

That is why every client makes you say which one you mean — u64(7) in Python, slate.Uint(7) in Go, uint(7n) in TypeScript — and why the TypeScript client refuses number for 64-bit integers entirely: above 2^53 a JavaScript number is not the integer you typed, and a primary key is where that shows up latest.

3 — The head node does not authenticate

In trusted-header mode the node reads three headers — principal, tenant, roles — and believes them. It is correct only behind a proxy that sets those headers itself and strips any the client sent.

There is no default: a configuration with no [auth] section is refused at startup rather than falling back to something. A repeated identity header is refused too, rather than resolved, because the server cannot tell whether the proxy in front of it appends or replaces.

What the node does enforce is authorisation. RBAC grants and row policies are compiled into the predicate the executor evaluates and the key bounds it scans, inside the kernel, on every access path — including index-only scans, aggregates and joins. There is no unauthenticated door, because every read and write takes a security context.

One consequence worth knowing: EXPLAIN is its own action and a blanket data grant deliberately excludes it. A plan is costed against statistics describing rows a policy may hide, so a caller who can vary a literal and watch the estimate move can recover values they cannot read.

4 — Sessions keep your reads from going backwards

Reads can be served by replicas, which lag. A session carries a watermark: it remembers the furthest point it has read or written, and sends that as a floor on later reads. Without it, a read after a write can be served by a node that has not caught up — correct, and surprising.

Every client turns this on by default and spells the opt-out at length (sessionWithoutMonotonicReads), so choosing the cheaper, surprising behaviour is deliberate.

5 — Errors carry a kind, and one is deliberately not retryable

Every client maps failures to the same closed set of kinds. Three are worth knowing:

  • not-leader is retryable elsewhere, and carries the node to try. It is distinguished from a plain outage because the remedy differs.
  • unknown-outcome is not retryable, on purpose. The write may have landed, and retrying is how one write becomes two.
  • deadline-exceeded has the same ambiguity as the above, and is treated the same way.
