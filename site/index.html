Rows, indexes and a planner,
on top of object storage.

A record layer for SlateDB: typed schemas, secondary indexes maintained in the same transaction as the row, a cost-based query planner, and row-level security enforced in the kernel rather than by a wrapper. The closest blueprint is FoundationDB's Record Layer, not an ORM.

Run it now

The front page is the database.

The kernel compiles to WebAssembly, so the planner and the executor run in your tab with no server behind them. The fixture is 100,000 real New York yellow-taxi trips from January 2024, joined to their own 265-zone lookup — fares, tips and missing passenger counts as published.

Every answer comes with the plan the cost model chose for it, and the Spec tab shows what your statement compiled to: the same structure the three clients send over gRPC.

What it does

A key's encoding is its index.

One ordered keyspace

Rows under one prefix, secondary index entries under another. There is no separate index structure, and index entries are written in the same transaction as the row — no background builder to fall behind, no repair path to get wrong.

A planner that costs

Table scans, index scans, point gets, ranges from IN lists and LIKE prefixes, covering scans that never touch a row, and histograms for range selectivity. EXPLAIN says which it picked.

Joins, aggregates, grouping

Hash and index nested-loop, cost-chosen, all four join types, chains of three or more tables, grouped joins and grouped chains, ordered and limited over groups, and HAVING.

Security in the kernel

Policies are compiled into the predicate the executor evaluates and into the bounds it scans — not checked by a wrapper a caller could step around. Every read and write takes a security context, so there is no unauthenticated door.

One writer, many readers

A gRPC head node holds a writer lease over the object store; replicas serve reads and a session's watermark keeps a caller's reads from going backwards.

Three clients that must agree

Python, Go and TypeScript, each tested against a real daemon — and a conformance runner that sends the same requests to all three and requires byte-identical answers. It found three divergences on its first run.

Where it stops

The things it is not.

Stated here rather than discovered later. The full list, with what each one would cost to close, is in the docs and in the repository's README.

Not published anywhere

Nothing here is on a package registry, and none of it is production-ready. It works end to end and is tested; that is a different claim.

Not SQL

The wire carries a query spec, not a string. The workbench's editor is a front end that compiles a SQL subset to that spec — it reaches joins, chains, grouping, HAVING, DISTINCT and IN (SELECT …), and stops at UNION, EXISTS and anything correlated, each refused by name with the reason.

Not one node's worth of write throughput

One writer holds the lease. Readers scale; writes do not, and a promotion is a restart rather than a handover in place.

Not measured everywhere it runs

The cost model was calibrated against a real S3 server at 200,000 rows. Nothing has been measured at a size where compaction, tiering and a cold cache all matter at once.
