    This is slate's own kernel compiled to WebAssembly — the planner, the executor and an in-memory store, running in this tab. There is no server.

    The data is real: 100,000 New York yellow-taxi trips from January 2024, sampled from the TLC's published month, joined to their own 265-zone lookup. Fares, tips and missing passenger counts are as published.

    slate has no SQL. What you type is parsed into its query spec, the same structure the Python, Go and TypeScript clients send, and the Spec tab shows what your statement compiled to.

    Writes land in this tab only. Reload, or press Reset data, to get the fixture back.

    The Storage tab shows what is actually stored: every row and index entry as a key, and the real S3 bucket those keys land in.

        Two views of the same data. The keyspace is what the record
        layer writes: one ordered key space, rows under one prefix and
        secondary index entries under another — there is no separate index
        structure. The bucket is what an operator sees: SlateDB batches
        those keys into SSTs, a write-ahead log and a manifest, and the object
        store holds files.
      
    
      
    
        The keyspace below is read live from the store in this tab, so it moves
        when you insert a row. The bucket listing is a real one, captured by
        seeding this same 100,000-trip sample into a real SlateDB store over a
        real object store —
        cargo run -p slate-slatedb --example bucket_layout — and
        shipped with the page. There is no SlateDB in a browser.
