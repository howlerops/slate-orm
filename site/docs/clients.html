Running it

Three clients that must agree

Three clients

Python, Go and TypeScript, tested against a real head node and against each other — one contract, three SDKs, identical answers.

The conformance runner

Every client's own suite runs against the same head node, which catches a client being wrong and cannot catch two clients quietly disagreeing about something the server accepts from both. The runner in examples/explorer/conformance sends the same requests to all three adapters and requires byte-identical JSON. It is the only thing in the repository that compares the clients to each other, and it found three real divergences on its first run.

It compares answers, not ergonomics — which is why it did not notice that two of the three clients passed no deadline on any RPC and could be made to block for ever. A check that agrees with itself is worth knowing the shape of.

Deadlines

None by default, in every client: adding one would turn a slow query into a failure in every caller that upgraded without asking for it. Each client spells it in its own language, and each names the unit in the parameter, because a caller reading one and writing another would otherwise be off by a thousand.

ClientHowUnit
PythonClient(timeout=…), session.with_timeout(…)seconds
Gocontext.WithTimeout — every method takes a contexta duration
TypeScriptclient.withTimeout(…)milliseconds

In Python and TypeScript it is a view rather than a setting: a new object over the same connection, so a short deadline cannot be left switched on by a caller who forgot to restore it. The deadline covers a whole streaming call rather than each message, which is why it is per call and not one number for the connection.

Decimals, and the conditional update

A decimal column holds a count of its own smallest unit, and the scale stays in the catalog — so 1250 is 12.50 at scale 2 and 1250 at scale 0, and nothing on the wire says which. Each client therefore has a units type rather than a number: Units in Python and Go, units() in TypeScript, with a renderer that takes the scale as an argument. A decimal.Decimal, a JavaScript number and a Go float are refused rather than scaled: there is no schema on the wire to reconcile their scale against the column's, and a client that guessed would be off by a power of ten.

The conditional update is optimistic concurrency, per row: send the row you want written alongside the row as you last read it, and the server compares the whole stored row and refuses with ABORTED if anything about it moved. Python spells it update(…, expected=…); Go and TypeScript spell it UpdateIfUnchanged / updateIfUnchanged, because their update is variadic over its rows and cannot take an optional argument.

A delete takes the same argument, because deleting a row somebody else just edited is the same class of mistake as overwriting it. It differs in one place worth knowing: a plain delete reports a key that is not there as affected: 0, because “make sure this is gone” is idempotent, and a conditional one refuses it with NOT_FOUND — a caller that said what it expected to find wants to hear that somebody got there first. NOT_FOUND and not ABORTED, because a row that moved can be re-read and the decision remade, and a row that is gone cannot, so a retry loop on ABORTED would spin. It guards the named row and nothing else: a cascade may still remove children the caller never saw.

Both used to be on the list of things the clients could not reach, along with relationships and keyset pagination, and none of the four is now. The three-SDK conformance runner compares all three clients on every one of them. What is still missing is here.
