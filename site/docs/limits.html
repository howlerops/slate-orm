Honesty

What it is not

Stated here rather than discovered later. The repository's README carries the full checklist, and docs/correctness.md has a section called What is still not proven — which itself went stale once, carried five closed items for a while, and says so now.

Not production-proven. Nothing runs this in anger. The correctness work is real and the operational track record is zero.

No SQL on the wire. Queries are built from typed client APIs and travel as a spec, not a string; the head node has no parser and no plan for one. The workbench does have a SQL front end, and it runs in the browser, compiling a subset to that same spec — joins, chains, grouping, HAVING, DISTINCT, OR and IN (SELECT …), stopping at UNION, EXISTS and anything correlated. Every stop is refused by name with the reason, which is the whole difference between a subset and a dialect.

AND and OR need brackets to mix. WHERE a = 1 OR b = 2 works on a single-table read, and so does WHERE (a = 1 OR b = 2) AND c = 3; both lower to the kernel's own tree. What is refused is an unbracketed mixture: a AND b OR c means (a AND b) OR c in SQL and reads as a AND (b OR c) to about half of everyone, so it is refused by name and the refusal says to write the brackets you mean.

Two clauses take no brackets. A join's WHERE is AND only: its conditions are split by side so each scan is narrowed before the hash join runs, and neither a disjunction nor a tree spanning both sides can be split that way. A HAVING is all AND or all OR — on a single table, a join and a chain alike — because the group conditions have no nested form to lower onto. A disjunction is also a filter rather than an access path: it cannot become a scan bound, because a = 1 OR b = 2 has no single key range.

The newest features stop where they stop. A window function is single-table — there is none over a join or a chain, and COUNT(DISTINCT …) over a moving frame is refused rather than approximated. An array column cannot be a primary key and cannot be indexed. Full-text search has no ranking, no stemming and no stop words: a match is a match. A view is read-only, cannot be defined over another view, and — unlike SECURITY DEFINER — cannot widen what a caller may see, because row-level security composes on top of it rather than under it.

No in-place promotion of a read replica to writer — promotion is a restart. No multi-writer. No cross-shard transactions, because there is no sharding.

The repository's README keeps a list of what is not built, and it is kept honest: an item is removed when it is built, or withdrawn in writing with the reasoning that retired it.
