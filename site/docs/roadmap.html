Honesty

Against the other ORMs

A feature audit against SQLAlchemy 2.0, Drizzle, Prisma, Ecto, ActiveRecord, Diesel and SeaORM, and a plan for the gaps worth closing. Every “we do not have this” below was checked against the source rather than remembered, and the full audit names the search that established each one — so that when this page goes stale, the next reader can re-run them instead of trusting it.

Three categories, and the difference matters

Missing

A thing developers expect that nothing here forbids. Work, and the plan below is about these.

Refused

A thing we could build and decided not to, with the reasoning written down. Not a backlog item — a decision to revisit only if the reasoning stops holding.

Forbidden

A thing the architecture rules out: one writer, no SQL on the wire. Work only if the architecture changes, which is a different conversation.

A feature list that does not draw those lines reads as a backlog of failures. Most of what follows is the first category.

What is already competitive

Stated first, because a gap list with no baseline is not an audit. Against those seven, slate is at or ahead of the field on:

  • A cost-based planner with EXPLAIN. None of the seven has one — they all delegate planning to the database.
  • Row-level security compiled into the predicate and the scan bounds, rather than checked by a wrapper a caller could step around.
  • Index entries written in the same transaction as the row, with no background builder and no repair path.
  • Batched relationship loading with no lazy fallback. There is no N+1 to fall into because there is no lazy load to trigger by accident — a stronger guarantee than Ecto’s preload or SQLAlchemy’s selectinload, which both sit beside a lazy loader.
  • Three client SDKs required to return byte-identical answers by a conformance runner. No ORM in the list does this, because none of them has three clients.

The two gaps that matter most

Predicate writes — UPDATE … WHERE and DELETE … WHERE

Built, in the kernel and the record layer. delete_where and update_where, with assignments evaluated over the row as it was read — so views = views + 1 is one write. On the wire too, as DeleteWhere and UpdateWhere with an optional RETURNING, and in all three clients. The description below is what was found before it was built, kept because the reasoning is what justified building it.

An update here is a row replacement: it names whole rows by primary key and writes them entire. There is no SET column = expression and no predicate form, and delete takes primary keys only. So DELETE FROM sessions WHERE expires_at < now() is not expressible — the caller queries the keys, carries them back, and deletes one per key, which is N+1 by construction and is not atomic with the query that found them.

The update half is worse. Without SET views = views + 1 the only way to increment a counter is read-modify-write, and two callers doing that lose one increment. update_if_unchanged makes the loss detectable — it is real optimistic concurrency and it works — but detecting a lost update and retrying is a worse answer than not losing it, and it is the answer we currently force.

Relations do not cross the wire

#[derive(Record)] accepts has_many and belongs_to and emits a Related impl, and load_related dedupes the key set and issues one read. That was reachable only from Rust when this was written: a Python, Go or TypeScript caller wrote the two-step fetch by hand, and the one who forgot wrote the N+1.

Built, as a Related RPC in all three clients. The one-level form, at least — many-to-many and nested loading were built afterwards in Rust and have not crossed the wire, which is why they are the first item of the next plan below. The same gap, one level deeper.

The rest, in rough order of what a user notices

This table was a list of gaps and nothing else, which made it wrong the moment any of them closed — and most of them have. The third column is what it stands at now; the long form of each, with the reasoning, is in docs/orm-comparison.md in the repository.

GapWho has itWhere it stands
Migrations generated from a schema diff Drizzle Kit, Prisma Migrate, Alembic Unblocked. The blocker was never the generator: the keyspace held a one-way hash of a table’s layout and not the layout, so there was nothing to diff. It stores the layout now, so a refusal names the column that moved and an additive change — appending a nullable column — is applied rather than refused, reading no row and rewriting none. What is left is whether a generator means anything here at all, since the catalog is the artifact and there is no migration file to emit.
Client code generated from the catalog Drizzle, Prisma Built. Row types, decoders and encoders in Python, Go and TypeScript, generated from --print-schema; CI regenerates and diffs them.
Validations, changesets, lifecycle hooks Ecto, ActiveRecord, SQLAlchemy Two of three built, one refused. A CHECK carries the column it is about and a message a form can show, every failing check is reported rather than the first, and all of it is published to clients. Lifecycle hooks are refused: arbitrary code on the daemon would not run for the Rust library embedding the kernel, so the rule would hold in one of two deployments.
Automatic created_at / updated_at ActiveRecord, Ecto, Prisma Built, in the store’s one write choke point rather than as a column default — a default cannot fire on update.
Window functions SQLAlchemy, Drizzle, Diesel Built in the kernel, not yet reachable. ROW_NUMBER, RANK, DENSE_RANK, LAG, LEAD and any aggregate over a partition, following SQL’s own frame rule — the whole partition without an ORDER BY, a running value through the current row’s peers with one. It had to be a new operator rather than a new aggregate: GROUP BY folds a row into its group and drops it, and a window keeps every row. It crosses the wire too — the value comes back in its own list, so a client does no ordinal arithmetic. What is left is the three client SDKs, which have no surface for it yet, and the query editor, whose own spec has no window field; it refuses OVER by name and says so.
CTEs and recursive queries SQLAlchemy, Drizzle, Diesel Answered: two thirds refused. WITH RECURSIVE is a fixpoint loop and a statement is one plan; a CTE read twice is the UNION argument exactly. A non-recursive CTE read once is missing, and is the same mechanism as views.
Set operations, views, arrays, full-text search most One built, one refused, two open. Arrays are built — stored, compared, sorted, generated in three languages and writable in a predicate. Set operations are refused, because the hard half of UNION is deduplicating across two independently planned statements. Views are designed and not built, and the design’s headline is that a view here cannot be a privilege boundary the way it is in Postgres. Full-text search is genuinely open, and larger than it looks: every index here writes one entry per row and an inverted index writes one per term, so it is a new index cardinality, not a new index expression.
Seeding, fixtures, factories Drizzle, Prisma, ActiveRecord Built in Rust, refused from a client. A factory generates rows from the table definition — types, nullability, defaults, sequenced keys, unique columns — and refuses by name what it cannot guess. It is not reachable from the wire on purpose: seeding writes as a superuser, and a client-reachable seed is a superuser write path from the network.

Refused, with the reasoning

Not gaps. Each is a decision with a written argument, and the argument is the thing to attack if you disagree.

  • Lazy loading. The single largest source of accidental N+1 in every ORM on the list. Not having it is why the batched load has nothing to fall back into.
  • Unit of work, identity map, dirty tracking. Implicit flush ordering is the hardest thing in SQLAlchemy to reason about, and the point of this layer is that a write is a write.
  • NOT EXISTS. Correlated by nature, like EXISTS, and refused with the NOT IN (SELECT …) form that asks the same question. NOT IN was on this list with it and is now built — the claim that three-valued IN made its negation mean something other than what a reader expects is withdrawn, since standard SQL's NOT IN is three-valued in exactly the same way.
  • SQL on the wire. The wire carries a spec, which is what makes the planner, EXPLAIN and the security compilation possible at all.

The first plan — six pieces, all built

Six pieces, ordered by value over cost. Each named what it was, how it would be tested, and where it stopped — the full version, with the alternatives weighed for each and a block on each saying what it became, is in docs/orm-comparison.md.

  1. Predicate writes in the kernel. — done. delete_where and update_where, the latter taking assignments over the row’s own values so views = views + 1 is one write. Tested by two oracles against a brute-force fold, by a policy test asserting a predicate write cannot touch a row the policy hides, and by a concurrency test that read-modify-write cannot pass — two increments make two, where read-modify-write makes one and update_if_unchanged makes an error. Eighteen mutations, no survivors; four of the eighteen survived the first pass and each became a test.
  2. Relations on the wire and in the three clients. — done. A Related RPC: the caller names a foreign key and sends a key per parent, and one read comes back grouped. The relationship lives in the catalog already — a foreign key encodes both directions — so clients name one rather than describe one, which is what stops them disagreeing about it. Seven cases in the conformance runner compare the three, including a parent with nothing related, a repeated key, and the backwards read as reader, where a row policy hides a book and all three have to lose it identically. Plus an assertion on the read count — fifty parents, one request, counted at the transport — because “one read, not N” is the whole claim. Thirteen mutations across the three clients, no survivors.
  3. Chains, keyset pagination and RETURNING on the wire. — done, and one third of it was a different feature. Chains were never missing: a JoinQuery carries as many inputs as it is given, so a chain needs no separate RPC, and all three clients already tested one. Keyset pagination is built — a cursor on the request, the next one on the response, page in all three clients — and every read it cannot page is refused by name rather than paged wrongly. RETURNING landed narrower than it was written: this wire’s rows are full width with no defaults, no auto-increment and no triggers, so an insert’s RETURNING would hand the caller its own request back. It exists on the two predicate writes, where the caller named a condition instead of the rows — and where, for a delete, the answer stops existing the moment the write lands.
  4. Many-to-many and has_many through. — done, and smaller than it looked. A many-to-many is the composition of two relationships the derive already emitted, so the capability needed no new declaration — only a name for which table stands in the middle, because a blanket impl over the two halves leaves the join type unconstrained and will not compile.
  5. Nested eager loading. — done, and the depth limit was refused. Each level of nesting is a type parameter, so a call’s depth is fixed when it compiles: a caller cannot ask for a thousand without writing a thousand types, and the refusal would guard nothing. It would be needed for an include list whose depth arrives as data, and nothing here parses one.
  6. Batch. — done. A network optimisation, not an atomicity guarantee, and the RPC makes confusing the two impossible: an unspecified atomicity is refused with a message naming both, because the two differ only when something fails. Fifty inserts singly took 46–49 ms and the same fifty batched took 4.9–5.1 ms across five runs — 9.4× to 10.0×, measured through the Rust wire rather than through a client.

The next plan

Six again, and four of them are debts the first six created: a capability that stops at the Rust edge, a response with no ceiling, a token only one code path can see, and a demo that shows none of it.

  1. through and nested loading on the wire. — done. The third time a capability had existed in Rust while the three clients did without it, and the last. A request now carries a path of relationships and the answer comes back one level per step, so an article’s tags through a join table is one call and two reads rather than two calls and a regrouping by hand. Every client rebuilds the tree the same way, from one number per level that says where the key sits in the level above — no catalog, no guessing. The depth is bounded, because on the wire a path’s depth is a number in a message and each step is a read.
  2. A ceiling on RETURNING. — done, and the hypothesis was right. It reproduced at 8,000 rows of about a kilobyte: the delete committed, every row was destroyed, and the caller got OutOfRange naming a 4 MiB decode limit — a known outcome turned into an unknown one. There is a configurable cap now, checked before anything is written, and it bounds the answer rather than the write: deleting a million rows is still a million rows deleted, and only asking to see them is refused.
  3. Keyset paging over a join or a chain. — done. Single-table reads had a cursor and a join still had an offset, which is the thing a cursor exists to replace: a row inserted between pages shifts every later page by one, and a caller walking a join sees a row twice or not at all.
    The design note came first, because what a join’s cursor is was the hard part — the driving side’s key is not unique once the join fans out. The answer: a page of a join is a page of its driving table. The cursor is the first input’s primary key, the limit counts its rows, and every joined row they produce comes back attached. Every joined row belongs to exactly one driving row, so reading each driving row once returns each joined row once — which is the guarantee the single-table cursor already had, reused rather than restated.
    The cursor deliberately is not a position in the result. Measured: only two of the three join algorithms return rows in the driving side’s order, and none does for a right or full outer join — so a cursor built on the output’s order would page differently depending on which plan the cost model happened to pick. A page is a range of keys instead, which every algorithm agrees about. The measurements are in docs/paging-a-join.md, and two of them corrected comments in the code that had been wrong since they were written.
  4. The stable reason token on the lone path. — done. All three clients dropped binary trailers, so the token reached a caller only when the failure was batched. It reaches one now on every failure, which is what lets a caller tell a predicate write refused for size apart from a join build, a sort or a group count — four different problems behind one status code, with four different fixes. Each client decodes the same blob captured off a running head node, and the three-SDK runner compares the token on every refusal it already tested.
  5. The demo shows the last three features. — done. Predicate writes, batch and relationships past one level were all invisible on the page that exists to show the surface. Three panels now, each showing what its feature is for rather than that it exists: a predicate write with returning turned off, so the count is all that is left of the rows it destroyed; both atomicities side by side, because the difference between them is the only thing a batch has to teach; and a two-step relationship path read as a tree and as its far rows, where a book with no editions is a level that is present and empty in one and absent in the other.
  6. Measure batching from a client. — done, and the prediction was backwards. The wire number did not go through a client, and the guess was that a client’s per-request work would eat into the saving. Measured, it is the reverse: 21–34× from Python, Go and TypeScript against the wire’s 15×. That work is paid per request, so it multiplies the one-at-a-time arm by a hundred and the batched arm by one — a client pays more per round trip, which is why saving them is worth more to a client and not less.
  7. Decimals and conditional updates across the wire. — done. The fourth time a capability had existed in Rust and reached no client, and the only one that had a test pinning the absence: value_to_proto turned a decimal into the string <unrepresentable decimal>, and the test’s own comment asked to be rewritten when the field arrived. Value now carries a decimal_value — an int64 count of the column’s smallest unit, the scale staying in the catalog — and UpdateRequest carries expected, dispatching to update_if_unchanged on all three write paths. All three clients have both. slate-serverd could not declare a decimal column at all until this: type = "decimal" was refused as “not a type”, so the feature existed in the library and not in the binary anybody runs, and it was found by trying to write a test fixture rather than by any check. Two mutations found the same missing test in two clients — a conditional update inside a transaction was only ever tested on the happy path, which an unconditional update satisfies identically.
  8. Deleting a row somebody else just edited. — done. delete_if_unchanged in the kernel, DeleteRequest.expected on the wire, and a conditional delete in all three clients — the same shape the conditional update has, because the argument is the same one. Where it stops being that update’s twin is the design content: a plain delete reports an absent key as zero affected, because “make sure this is gone” is idempotent; a conditional one refuses it, and refuses it as NOT_FOUND rather than ABORTED. A row that moved can be re-read and the decision remade; a row that is gone cannot, so a caller retrying on ABORTED would spin. The three-SDK corpus compares that distinction, which is the one place the three clients’ error taxonomies meet on a code no other endpoint produces.
  9. Arithmetic over money, and a decimal literal in SQL. — done. Two roadmap lines that read as unrelated — price * quantity was not expressible, and WHERE total > 19.99 parsed as a float — and are the same fact: a decimal is a count of a unit the column names, and neither the expression layer nor the parser knew that. The rule is now one sentence: an expression is expressible when its answer is still a count of the same unit its operands were counts of, and everything else is refused at plan time rather than returning a column of nulls. Three things came out of building it. The check first lived in Reads::execute, which EXPLAIN does not go through — so a plan came back for a query that could not run, which is worse than an error because it looks like an answer. Mul and Div asked only whether a side had a scale, so price * Decimal(3) planned cleanly and evaluated to null on every row. And the SQL half reads 19.99 by splitting on the point, because the obvious parse::<f64>() * 100.0 reads "8.20" as 819 cents — a test in the tree rather than a claim in a comment.

What neither plan does

Neither closes the whole table. Window functions, CTEs, views, arrays, full-text search and set operations are all real absences and none is in either six: they are planner work of a different size, and doing any of them before predicate writes and wire relations would have been building the interesting thing instead of the needed one. The second six has a narrower version of the same argument — every item in it is an edge the first six left unfinished, and finishing what shipped beats starting what has not.

It also leaves out validations and lifecycle hooks, which are a design question rather than a missing function — where does validation live when three clients in three languages share one catalog? The honest answer is that we have not worked it out, and somebody should write that design note before any of it is built.
