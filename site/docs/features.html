The database

What it does

Every item here is reachable from the Rust record layer. Which of them cross the wire to the Python, Go and TypeScript clients is a separate question, and the clients page answers it.

Reading

A planner that costs

Table scans, index scans, point gets, ranges from IN lists and LIKE prefixes, covering scans that never touch a row, and histograms for range selectivity.

Joins and aggregates

Hash and index nested-loop, cost-chosen, all four join types, chains of three or more tables, grouped joins and grouped chains, ordered and limited over groups, and HAVING to filter them.

A grouping with no keys is one group over every row, which is what SELECT count(*) FROM trips means. A grouping with keys and no aggregates is the other end of the same dial: SELECT DISTINCT. Both were front-end refusals over a kernel that had always answered them.

So DISTINCT is not an operator here — it lowers to GROUP BY over the columns selected, and the Spec tab shows exactly that. Asking for both is refused: they are one request written twice. SELECT DISTINCT * is refused too, with the reason — every table has a primary key, so the rows are already distinct and the grouping would cost a full pass to return what it was given.

It crosses the wire as well: group keys with no aggregates, from Python, Go or TypeScript. The head node used to refuse that on the aggregates alone, which was right about the case it was written for — no keys and no aggregates asks for one group with nothing in it — and wrong about this one.

Subqueries, in one shape

WHERE author_id IN (SELECT id FROM authors WHERE country = 'US') works, and nothing about it reached the kernel. The inner query runs once, before the outer one; its single column becomes the values of an ordinary IN; and the planner's existing handling of that — point gets on a key, a range on an index, a hash set on a scan — does the rest. The Spec tab shows both halves: the subquery as written, and the candidate list it produced, so a surprising answer can be read back to whichever of the two caused it.

One shape, and the edges are refusals rather than approximations. A correlated subquery cannot work at all here, because the inner query runs once and would have to run per outer row — and it fails naturally, since a column of the outer table is simply not a column of the inner one. EXISTS is correlated by nature and is refused with the IN form that expresses the same question, and NOT EXISTS with the NOT IN (SELECT …) form for the same reason.

NOT IN itself works, and used to be refused on a claim since withdrawn: that the kernel's three-valued IN — a null in the list makes the answer unknown rather than false — meant its negation would not mean what a reader expects. Standard SQL's NOT IN is three-valued in exactly the same way, so the surprise belongs to SQL rather than to this implementation, and negating unknown gives unknown. The planner was the part worth checking: it derives no access path from an IN inside a NOT, which is the only correct answer, since the complement of a set of points is neither a range nor a set of points.

A candidate whose type could never equal the outer column — title IN (SELECT id FROM authors) — is refused at parse time rather than answered with nothing. That query errors nowhere downstream: 1 renders to text and parses back as the string "1", which no title equals, and zero rows with no complaint is indistinguishable from a fact about the data. Mixed integer widths are allowed, because they round-trip and refusing them would refuse a query that works.

UNION, INTERSECT and EXCEPT are refused by name too. A statement compiles to one query spec — one table, one filter set, one plan, the same structure the three clients put on the wire — and the spec has no set operator, so there is nowhere to lower one onto. Two statements separated by ; run both halves and show both plans, which gets everything but the deduplication.

Computed columns

hour(), day_of_week(), year() and the rest are evaluated per row and group, sort and filter like any column, on a single table or on a join. There is no date type: a timestamp is seconds since the epoch in an integer column.

On a join, every position is resolved in the joined row: the group key, the computed column and the aggregates may each read either table, and a qualified name like zones.id picks its side. So SELECT hour(pickup_time), avg(fare) … FROM trips JOIN zones works, where a key on one side and an aggregate on the other used to be the only shape available. An unqualified name that both tables have resolves to the left one and says so above the results, rather than choosing in silence.

A grouped join can be ordered — ORDER BY count(*) DESC — and the ordering is over the groups: a group is its key followed by its aggregates. An ungrouped join cannot be ordered at all, and says why: the kernel orders groups, not joined rows.

They read UTC unless given a second argument: a fixed offset, hour(pickup_time, '-05:00'), or a named zone, hour(pickup_time, 'America/New_York'). A name is resolved against a transition table built from IANA's tzdata — a few kilobytes of sorted integers for a curated list of zones, not the whole database — so daylight saving is looked up at each row's instant rather than guessed at. A zone outside the list is refused, and the refusal names the ones that are in it. The taxi sample in the workbench is New York wall clock already, which is why its quietest hour is 04:00 and not 09:00.

Relationships, loaded not lazy

#[record(has_many(Book, foreign = author_id))] declares one, and load_related fetches every parent's children in one read — measured at 1 scan where the per-parent loop it replaces takes 3. There is deliberately no lazy accessor: the feature an ORM is judged on and the N+1 it is blamed for are the same feature, because an accessor cannot tell whether it is being called once or ten thousand times.

Columns are named by field ident, not by string, so a typo is a compile error on both sides rather than a panic on first use.

Windows, a value per row

row_number(), rank(), dense_rank(), lag(), lead() and the aggregates, over a PARTITION BY and an order: SELECT title, rank() OVER (PARTITION BY author ORDER BY sales DESC) FROM books. A window is row-preserving — every input row comes back with a value attached — which is what separates it from GROUP BY, where rows collapse.

It crosses the wire in its own list and all three clients can build one. A window is single-table. There is no window over a join or a chain, in the kernel or on the wire, and asking for one is refused rather than silently dropped. COUNT(DISTINCT …) OVER (… ORDER BY …) is refused too: a distinct count over a moving frame is a different algorithm, and guessing it would be worse than saying no.

Full-text, one entry per term

WHERE title CONTAINS 'the heaven', backed by an index declared text = true. This is a new index shape rather than a new expression: every other index here writes one entry per row, and an inverted index writes one per term per row — so the write path, the unique-slot check, the delete path and the planner all had to stop assuming that cardinality.

The planner ranges the inverted index on one term and filters the rest, so a two-word phrase narrows by its first word and checks the second per row. No ranking, no stemming and no stop words: a match is a match, in the order the index walks.

Views, named and read-only

A view is a named query, declared as [[views]] in the server's TOML and validated when it loads — not a CREATE VIEW over the wire, because the wire carries no SQL. A read naming a view gets the view's filter AND its own, and the order does not matter.

A view is sugar, not a grant. It cannot widen what a caller may see: row-level security still composes on top, so a view over a table the caller cannot read returns nothing rather than leaking it. That is the opposite of what most SQL databases do with SECURITY DEFINER, and it is worth knowing before you design around it. Writes through a view are refused by construction, as is a view whose own FROM names another view.

Pages that do not shift

OFFSET reads and discards every row it skips, and counts rows — so a row deleted between two pages makes the reader silently miss one. A cursor is the last row's primary key and narrows the scan range instead: page 99 of 100 read 5 key-value pairs against the offset version's 495, and the deleted-row case is asserted both ways round.

page_records in Rust, and page in all three clients, return the rows and the cursor for the next page — so a caller never names a key column. The server builds the cursor, because building one means knowing which columns are the primary key and in what order, and a cursor built from the wrong column still pages: just through the wrong sequence.

A sorted query, a grouped read, and a projection that drops a key column are all refused by name rather than paged wrongly. The last of those is what the server building the cursor costs: there would be no key to build one from, and serving the page without a cursor is the silent version — the caller loops until the cursor is absent, gets none on the first page, and reads one page of a large table as the whole answer.

Writing

Conditional writes

The store detects two writers overlapping in time. The common failure is the other one: read a row, decide, write it in a later transaction while somebody else wrote it in between. Nothing overlaps, so nothing is detected, and an edit is silently lost. replace_record(&previous, &next) writes only if the stored row still equals what was read.

Soft delete, and a real purge

A table marked soft_delete retires a row instead of erasing it: reads skip it, the primary key stays taken, and every write path treats it consistently rather than one of them forgetting. Reading retired rows needs include_deleted, which is a privileged read rather than a flag anyone can set, and a retired row can be restored.

Retired rows are not immortal: purge_deleted erases them past a retention window, and the purge is counted in /metrics like any other write. A RESTRICT foreign key still blocks on a retired child — the row is hidden, not gone, and pretending otherwise would let a delete orphan a reference.

Migrations, before the socket opens

Adding an index to a populated table used to make queries through it return nothing — no error, rows still on disk, and intermittently, depending on whether the index covered the query. Schema state now lives in its own keyspace, and the daemon reconciles before it binds its listener: a node that binds first accepts a connection and answers it wrongly.

[schema] migrate_on_start = false makes it verify and refuse to start instead, which is not the same as skipping.

Types

Exact decimals

A hundred rows of ten cents sum to exactly $10.00; the same rows as f64 give 9.99999999999998. Both are asserted, because a test that only showed the right answer would not establish there was anything to fix.

The scale lives on the column, so a decimal is an integer count of the smallest unit: it encodes as an integer, the ordering is the integer ordering, and SUM is exact. The cost is that a value cannot print itself — rendering needs the column.

That cost is what every client's decimal surface is shaped around. [[tables]] declares one as { name = "price", type = "decimal", scale = 2 }, with the scale required there: a decimal column that meant scale 2 and got 0 stores every value a hundred times too large, is internally consistent, and is discovered by an accountant. The wire carries the units and never the scale, so a client restates it locally — and the schema fingerprint is what checks that the two agree. A scale is the one property in that hash which addresses no column, and it is there because the failure it prevents is worse than the one the hash's usual rule is about: a wrong ordinal reads the wrong column and shows, a wrong scale reads the right column and renders every value a power of ten out, for ever, with nothing anywhere reporting it.

Arithmetic follows from the same fact. An expression over a decimal is expressible when its answer is still a count of the same unit its operands were counts of: price * quantity is (cents times a plain count is cents), price - discount is when both are at one scale, total / parts is (truncating toward zero, because there is no scale to round to), and a decimal literal has no scale of its own so price - 0.50 takes the column's. price * discount is not: cents times cents is hundredths of a cent, at a scale no column has and nothing on the wire could carry. Nor is price + quantity, which is money plus a count of nothing.

The refusals arrive at plan time, naming the operation and what to write instead, rather than as a column of nulls at the far end — which is indistinguishable from a column that is legitimately null. SQL reads a number with a point in it at the column's scale, so WHERE price > 19.99 against a scale-2 column compares 1999 units exactly, and 19.830 finds the same row as 19.83. You can type that into the workbench.

Arrays, ordered by prefix

A column can hold a list, with the element type on the column rather than in the type: tags is an array of strings, not a distinct ArrayOfString. Arrays compare lexicographically with shorter-is-less, so [1] sorts before [1, 2] before [2] — prefix order, the way a word list sorts.

That ordering is why the encoding terminates an array rather than prefixing its length. A length prefix would sort [2] before [1, 2], because one is less than two before any element is compared, and the tuple codec's whole contract is that byte order is value order.

An array cannot be a key or be indexed. Both are refused rather than half-supported: indexing a list is the inverted index above, which is a different shape with a different cost, and conflating the two would make one of them quietly wrong.

Timestamps the store writes

#[record(created_at)] and #[record(updated_at)] on an i64 field, or { name = "created_at", type = "i64", managed = "created_at" } in the daemon's TOML. The store fills both on insert; on every write after that updated_at moves and created_at does not.

The value you send is discarded. Not filled-in-if-null — overwritten, on insert and on update. Honouring a supplied value is what makes importing rows with their original times possible and it is the wrong default: the whole promise of the column is that it says when the row was written, and a client that can set it can break that promise with nothing downstream able to tell a real timestamp from a claimed one. An import that needs the original times declares the column unmanaged and writes them, which is one word in a schema against a hazard on every write of every managed column.

This is not a DEFAULT, because a default is a stored value and the wanted value is "whatever the clock says at the moment of the write". Widening defaults to hold an expression would mean a second expression language in the schema layer, evaluated on a path that evaluates nothing today, to express two cases.

Seconds, like every other time here, so date_trunc and the calendar functions read it correctly. The cost is real and worth stating: two writes in the same second give the same updated_at, so it cannot order writes within a second or serve as a concurrency token. update_if_unchanged is the thing for that, and it compares the whole row.

The schema layer refuses a managed column that is not an i64, is nullable, or is in the primary key — all three at build time, so a node with one does not start rather than surprising somebody on their first insert. It is not in the schema fingerprint, on the rule the fingerprint already follows: a client that disagrees still reaches the right column, and the disagreement shows immediately, because it reads back a value it did not write.

No date type, and an enum is its own name

The value model is closed — nine types, each one the tuple codec can order — so a Rust type that needs storing gets a mapping onto an existing one rather than a tenth. A Timestamp is an i64 of seconds: chronological order is integer order, already proven, and every calendar function reads seconds. #[derive(Enum)] stores the variant name in a Str.

A name rather than an ordinal because the two fail differently. Reordering variants silently reinterprets every stored row, and reordering is an accident — alphabetising, inserting in the middle. Renaming does the same damage but is deliberate, and the compiler makes you visit every use site. rename lets the Rust spelling and the stored one move apart.

Json<T> is a string that happens to hold JSON, and every query against it is a query against that string. There is no path expression: a document has no useful total order, so it could not be a key, an index or a range. If a field inside needs querying, it is a column.
