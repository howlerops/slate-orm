Running it

One writer, many readers

One writer, many readers

A lease-fenced writer and read replicas, with read tokens so a session never reads its own writes backwards.

The lease

Writer leadership is a lease held in the object store, with a fenced generation number. A node that loses the lease and keeps writing is fenced by the store rather than by its own belief about whether it is still the leader, which is the failure every lease design has to answer for.

A commit that times out becomes UNKNOWN and not DEADLINE_EXCEEDED, precisely so that a client does not retry a write that may already have landed. All three clients classify it as not retryable, and say so in their error documentation.

Reads that do not go backwards

Replicas serve reads from a snapshot that may lag the writer. A session carries a watermark — the highest sequence it has observed, from its own commits and from the views that served its reads — and every read carries it as a freshness floor. That is what makes a write followed by a read see the write without the caller naming a token.

The watermark is readable and settable, so a job queue can hand "read at least what I wrote" to a worker. No amount of implicit threading covers that case, which is why it is in the API rather than only in the machinery.

Configuration is one file

slate-serverd --config head.toml, and --check validates without starting. The quickstart has a complete one. Two knobs worth knowing about before you deploy:

  • [schema] migrate_on_start defaults to true, and the node reconciles before it binds its listener — a node that binds first accepts a connection and answers it wrongly. Setting it to false makes the node verify and refuse to start, which is not the same as skipping.
  • [auth] mode decides where identity comes from. There is no mode in which the head node authenticates anybody; see security.
