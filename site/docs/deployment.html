Running it

One writer, many readers

One writer, many readers

A lease-fenced writer and read replicas, with read tokens so a session never reads its own writes backwards.

The lease

Writer leadership is a lease held in the object store, with a fenced generation number. A node that loses the lease and keeps writing is fenced by the store rather than by its own belief about whether it is still the leader, which is the failure every lease design has to answer for.

A commit that times out becomes UNKNOWN and not DEADLINE_EXCEEDED, precisely so that a client does not retry a write that may already have landed. All three clients classify it as not retryable, and say so in their error documentation.

Reads that do not go backwards

Replicas serve reads from a snapshot that may lag the writer. A session carries a watermark — the highest sequence it has observed, from its own commits and from the views that served its reads — and every read carries it as a freshness floor. That is what makes a write followed by a read see the write without the caller naming a token.

The watermark is readable and settable, so a job queue can hand "read at least what I wrote" to a worker. No amount of implicit threading covers that case, which is why it is in the API rather than only in the machinery.

Configuration is one file

slate-serverd --config head.toml, and --check validates without starting. The quickstart has a complete one. Two knobs worth knowing about before you deploy:

  • [schema] migrate_on_start defaults to true, and the node reconciles before it binds its listener — a node that binds first accepts a connection and answers it wrongly. Setting it to false makes the node verify and refuse to start, which is not the same as skipping.
  • [auth] mode decides where identity comes from. There is no mode in which the head node authenticates anybody; see security.

What the node tells you

By default: its startup, its warnings, and nothing per request. Two settings open that up, and both are off unless you say otherwise — a node that starts logging differently because it was upgraded is a surprise, and a line per request on a node serving ten thousand a second is a hundred megabytes an hour of stderr nobody asked for. 

[observability]
request_log = true          # one line per request
summary_interval = "60s"    # per-method counters, this often
  • request_log writes slate-serverd: /slate.v1.Records/Query id=3f2504e04f89 status=0 head=1.4ms per call. A debugging tool rather than something to leave on.
  • summary_interval writes one line per method that has been called — calls, failures, late failures, the mean, the p50, p90 and p99, and the slowest — on that cadence, and once more on the way out so the last interval is not lost. Cheap at any request rate, and the one a production node should have on.
  • The quantiles are written p99_head<= because they are read out of a histogram eight buckets to the octave: the number is an upper bound on the true one, never more than an eighth over it and never under. slowest_head is exact, and a quantile is clamped to it, so a p99 never prints above a maximum the same line reports.
  • late is the subset of failed that arrived after the response head — a streamed read that answered rows and then died. It is counted apart because it points somewhere else: a head failure is a request the node refused, and a late one is a scan that broke under it.
  • A row named (other) means the node has seen more than 64 distinct request paths and is pooling the rest. Nineteen methods exist, so in practice this only appears when somebody is sending paths that do not resolve — the counters are keyed on the path, and the cap is what stops a stranger growing them without bound. Nothing is lost: the calls are counted, just not named.

The id is the caller's own: all three clients send a fresh one per call in slate-request-id, and put it on every error they raise, so a caller holding a failure can grep the log for its line. A call that sent none logs id=-, and the field is always present so the columns do not move.

The value is filtered before it reaches the line, to [A-Za-z0-9._:-] and 64 characters. It is attacker-controlled text on its way into an audit trail: gRPC itself refuses a newline in a header, but not a space, a quote or an =, so an unfiltered id of x status=0 would give a reader two status= to choose between. Forged lines in a log are worse than no log, because they are believed.

Both times are to the response head, not to the last row: a streaming read returns its head immediately and then streams for as long as the client keeps reading, so timing to the end would measure the client's appetite rather than the server's work. The log line says head= for that reason. A failure raised in a trailer, after the head was already sent, is invisible to this and counts as a success.
