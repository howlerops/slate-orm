# The tree says 0.2.0, ready for a tag that publishes all five artefacts

- **Date:** 2026-10-05
- **Author:** Claude Code (session: the owner, on finding npm and PyPI empty: "ok, let's do those")
- **Touches:** `Cargo.toml`, `Cargo.lock`, `crates/slate-serverd/Cargo.toml`,
  `clients/typescript/package.json`, `clients/typescript/package-lock.json`,
  `clients/python/pyproject.toml`, `scripts/mutations.json`,
  `docs/releasing.md`
- **Kind:** process

## What changed

The version is 0.2.0 everywhere `scripts/check_versions.py` reads it:
- the workspace;
- the six `path = …, version = …` requirements in the root manifest;
- `slate-serverd`'s own requirement on `slate-server`;
- the npm package and its lockfile;
- the Python project.

The roster mutation that anchors on the npm manifest's version line moves
with it. No tag is pushed by this change.

## Why

The owner asked whether every client is available for use. Checked against
the registries:
- the Go module (`v0.1.0` on `proxy.golang.org`), the image (`0.1.0` and
  `latest` on GHCR) and the binaries are out;
- npm and PyPI answer 404, because `vars.PUBLISH_NPM` and
  `vars.PUBLISH_PYPI` were never set.

Everything shipped is from `419378d`, before column grants reached the
clients and before the gRPC-web transport and the `./edge` entry existed.
The owner chose to turn both registries on and cut the next release.
`docs/releasing.md` says why the number has to move first: a version cannot
be reused on npm or PyPI, `0.1.0` already shipped without them, and a tag on
a tree that still says `0.1.0` would publish `0.1.0`.

## Alternatives rejected

- **Tag now, and turn npm and PyPI on afterwards.** The publish jobs run
  only on a `v*` tag push, so they would need a second tag and a second
  number. One tag, after the account steps, ships all five artefacts at
  `0.2.0` in one run, which the release's last job then reports on.
- **Set `PUBLISH_NPM` and `PUBLISH_PYPI` now.** With the variable `true` and
  no credential, the job fails by design (`docs/releasing.md`, "Turning npm
  and PyPI on"). Setting them before the scope is claimed and the token and
  Trusted Publisher exist would turn the next tagged release red for a
  reason already known.
- **`0.1.1`.** Column grants, the edge entry and a second transport are new
  API in all three clients, not a fix, so the minor version moves.

## Evidence

- `python3 scripts/check_versions.py v0.2.0`: "ok 0.2.0 in Cargo.toml,
  clients/python/pyproject.toml and clients/typescript/package.json,
  inherited by 14 workspace member(s), and 1 tag(s)".
- `cargo metadata` first refused, because `slate-serverd` requires
  `slate-server = "^0.1.0"` on its own line, which `docs/releasing.md`'s bump
  list did not name. The list names it now.
- `Cargo.lock` moved exactly the 14 workspace members, and nothing else.
- The roster mutation, re-anchored to `0.2.0` → `0.2.1` and run through
  `mutate_guard.py`, is caught by `check_versions`;
  `check_mutations_roster.py` passes.

## What this does not do

- **Nothing is published by this commit.** It needs the npm scope and token,
  the PyPI Trusted Publisher and both variables, all of them owner account
  actions, and then the `v0.2.0` tag.
- **`docs/releasing.md`'s table of what shipped still describes `v0.1.0`.**
  It records a measurement of that release, and the `v0.2.0` row belongs to
  whoever asks the registries after the tag runs.
