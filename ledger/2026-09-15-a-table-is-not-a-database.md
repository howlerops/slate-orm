# Named timezones resolve through a generated transition table, so `hour(t, 'America/New_York')` knows about daylight saving instead of being refused

- **Date:** 2026-09-15
- **Author:** Claude, working from "I don't want any gaps. Please address those"
- **Touches:** `slate-kernel` (`scalar.rs`, new `zones.rs` + generator, new tests), `slate-server` (proto, `convert.rs`, `wire.rs`), `slate-wasm` (`lib.rs`, `sql.rs`, `datetime.rs`), all three clients, `site/docs.html`
- **Kind:** feature

## What changed

`Scalar::ZoneShift { zone, value }` adds a named zone's offset *at that
instant* to a timestamp, so every calendar scalar above it reads the local wall
clock with no change of its own. The offsets come from
`crates/slate-kernel/src/zones.rs`, generated by
`crates/slate-kernel/scripts/generate_zones.py` from the system's IANA
`tzdata`: fourteen zones, 2,822 transitions, 1900–2100, about 76 KB of sorted
integers. The variant is on the wire as `ZoneShift`, refused by name at the
gRPC boundary and in the wasm binding when the table does not have it, and
reachable from all three clients (`in_zone`, `InZone`, `inZone`) and from the
SQL front end as a second argument to any time function —
`hour(pickup_time, 'America/New_York')` beside the existing
`hour(pickup_time, '-05:00')`.

## Why

The front end refused a region name twice, with a reason that read well: there
is no timezone database here, so `America/New_York` could only be honoured by
guessing at daylight saving, and guessing is wrong for a third of the year. The
reason was true of a *database* — megabytes, a parser, a release cadence, in a
binding whose point is that it fits in a browser tab — and not true of a
*table*. A lookup needs a sorted list of instants and offsets. For the zones
anyone actually asks about that is a few kilobytes, which is less than the
`regex` crate the kernel already carries for `RegexpReplace`.

The gap was not cosmetic. The taxi sample is New York wall clock stored as
UTC-looking seconds, and the only way to ask "which hour of the *local* day"
was to write `-05:00` and be wrong from March to November. Anyone extending the
sample past January would have got a silently shifted answer.

## Alternatives rejected

**Ship the IANA database and a TZif parser.** Correct for every zone and every
year, and the honest cost is a second binary format to be wrong in, a
megabytes-scale asset in a wasm bundle that is currently 1.6 MB, and a release
cadence — `tzdata` revises several times a year. The table is a snapshot of the
same data with the parser run once, at generation time, on a machine that has
`zoneinfo`. What it gives up is zones outside the list (refused by name, with
the list) and rule changes after the file was generated (a projection, and the
module says so in its own header).

**A zone field on each of `Extract`, `DateTrunc`, `CalendarPart` and
`CalendarTrunc`.** Four fields instead of one variant, and four places for the
planner, the covering-scan analysis, the wire conversion and the round-trip
property to each grow a case. The shift *composes* — it is a scalar wrapping a
scalar — so every one of those paths already handles it. This is the same
argument that made the fixed offset need no kernel support at all
(`Scalar::Add` of a constant); the only reason a zone needs a variant is that
the addend is not a constant.

**Compute the rules rather than tabulate them** — "second Sunday in March,
first Sunday in November", evaluated per row. Smaller than a table and wrong:
the United States moved those boundaries in 2007, the European Union keeps
voting on abolishing the change, and Arizona opted out in 1968. A rule-based
implementation gives the right answer for recent years in the zones whose rules
you encoded and a confidently wrong one everywhere else. The 2007 change is a
test here precisely because it is the fact a projected table gets wrong.

**Byte-compare the generated file against a regeneration**, as the protobuf
stub tests do. Rejected because the input is not in the repository. The stub
tests can byte-compare because their `.proto` is committed, so a difference
means the generator moved; here a byte compare would go red on a comment, on
the version string in the header, and on a `cargo fmt` from a newer toolchain —
the `grpcio-tools` failure this repository already has written up. `--check`
compares the *pairs*, which fails on exactly one thing: the committed table no
longer saying what `tzdata` says. That still goes red when IANA revises a rule,
and that red is correct — the table really is stale and the fix really is to
regenerate.

**Let the clients carry the zone list** so a bad name fails locally. Rejected:
three copies of a list that the server owns, going stale silently and
independently. The clients send the name as a string and the refusal is the
answer, which is also what this protocol does everywhere else — `SchemaCheck`
is an assertion rather than a query for the same reason.

## Evidence

**Two of my own assertions were wrong about real history, and the table was
right.** `every_table_is_sorted_and_covers_the_window` asserted every zone has
a transition near 2100; America/Phoenix's table stops in 1967, because Arizona
opted out. `no_transition_moves_the_clock_by_more_than_a_few_hours` asserted
every offset is a whole number of minutes; Asia/Kathmandu's 1900 offset is
+05:41:16, local mean time before standardisation. Both are now stated facts
rather than slack: `STOPPED_CHANGING` pins the year each of four zones stopped
and requires every *other* zone to still be moving at the window's end, which
is stricter than the bound it replaced, and the whole-minute check exempts only
the opening entry (Paris +00:09:21, Kolkata +05:21:10, Kathmandu +05:41:16 —
all three checkable with `zoneinfo`).

**Mutation testing the lookup, five mutations:**

| mutation | caught by |
| --- | --- |
| `*when <= instant` → `*when < instant` | **survived** |
| drop `.saturating_sub(1)` | 7 named tests |
| `.get(at)` → `.get(at + 1)` | 7 named tests |
| `saturating_add(offset)` → `saturating_sub` | 6 named tests |
| unknown zone → `I64(seconds)` instead of null | `an_unknown_zone_is_null` |

The survivor is the interesting one: an inclusive bound written exclusively is
right everywhere except at a transition's own second, which is one second in
fifteen million and never hit by a test aimed at the middle of a season.
`a_transition_takes_effect_at_its_own_second` closes it, asserting both New
York 2024 transitions from either direction; with it the mutation fails.

**Mutation testing the freshness check, three mutations,** all caught with the
offending zone and instant named: one offset changed (`America/New_York: first
at (1710054000, -14500) in the file against (1710054000, -14400) fresh`), one
transition deleted, one zone dropped from `ZONES`. Fixing the second of those
found a real bug in the checker: `static UTC: ... = &[(-2208988800, 0)];` is one
line after `rustfmt`, and a regex anchoring the close bracket to a line start
made UTC's table swallow New York's — 13 zones parsed instead of 14.

**The SQL front end against the sample, two ways.** January 2024 is wholly
Eastern Standard Time, so `hour(t, 'America/New_York')` and
`hour(t, '-05:00')` must agree over all 100,000 trips: they do, and both agree
with an independent fold over the decoded file. That is a differential between
a binary search and arithmetic on a constant, which is as separate as the two
paths get. `Australia/Sydney` is the control: UTC+11 in January, eleven hours
the other way, checked against its own fold — a lookup that had quietly become
a constant −5 fails there.

**The wire:** `a_computed_value_survives_the_round_trip` now draws zones from
the table itself, so the strategy grows with it, and the exhaustive `Scalar`
match in `wire.rs` failed to compile until `ZoneShift` was handled — which is
the guard working as designed. `a_zone_the_server_does_not_have_is_refused_by_name`
checks four bad names including `america/new_york`, and that the refusal
carries the list.

**Suites:** `slate-kernel` all green (12 tests in `zones.rs`, 2 in
`zones_generated.rs`), `slate-wasm` `datetime.rs` 31 green.

## What this does not do

**Fourteen zones, not six hundred.** UTC, four US zones plus Phoenix, three
European, Tokyo, Kolkata, Kathmandu, Sydney, Auckland. Chosen for the *shapes* a
zone can have — northern and southern DST, no DST, half- and quarter-hour
offsets, a zone that stopped changing — rather than for coverage. Adding one is
a line in the generator's list and a regeneration.

**Transitions after 2026 are projections.** The rules as they stand, run
forward. A query about 2087 is answered from today's rules, which is the best
anyone can do; the module header says so rather than implying otherwise.

**No ambiguous-time handling.** When a clock falls back, 01:30 happens twice,
and this answers with the offset in force at the UTC instant — which is exact
for a stored UTC timestamp and has no way to express "ambiguous" for a *local*
one. There is no local-timestamp type here, so the question does not arise yet.

**The reverse direction is missing.** `in_zone` turns UTC into local seconds;
nothing turns a local wall-clock time back into a UTC instant. That needs the
inverse lookup, which is where the ambiguity above becomes real, and no caller
has asked for it.

**No zone on a literal in the SQL front end's `WHERE`.** The second argument is
accepted on time functions in the select list and group key, as before; a
filter still compares against a stored timestamp in UTC.

**`tests/zones_generated.rs` needs `python3` and a system `tzdata`.** It fails
rather than skipping when either is missing, deliberately — a skipped freshness
check reads as a passing one. CI's `ubuntu-latest` has both.
