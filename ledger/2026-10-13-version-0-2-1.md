## What changed

Every manifest moves from 0.2.0 to 0.2.1. That is the same five files and
28 lines the 0.2.0 bump touched, and `check_versions.py` accepts both the tree
and the tag `v0.2.1`. The roster mutation that drifts the npm package's
version is re-anchored to 0.2.1 → 0.2.2 and was caught.

`docs/performance.md` gains §8f, a comparison of SlateDB 0.16 and 0.17 on
the three examples the dependency sweep rests on. The two caveats in the 0.17
entry get verdicts. CI had refused both as `open`, because the backlog has
been held at zero since 2026-10-01:
- *The rest of 0.17 is unmeasured* is `closed`, with §8f as its witness.
- *v0.2.0 still ships SlateDB 0.16* is `moment`. It describes what was
  published on the day, and the release cut from this tree is its answer.

## Why

The previous entry left two things undone and named them. The owner asked
for both to be addressed and for everything to move to the newer SlateDB.
Moving everything means a release: the binaries, the image, the Go module and
the npm and PyPI packages all embed or serve the head node that carries
SlateDB. Nothing published can change without a new version number, because
npm and PyPI refuse a reused one.

Before a release, and before redeploying the live explorer over a bucket
that 0.16 wrote, one question had to be answered by test rather than by
reading release notes: can 0.17 open a 0.16 bucket, and can 0.16 still read
what 0.17 wrote? The second direction matters because a rolling deploy runs
both versions against one bucket for a while. A head node is also never
upgraded in place, only restarted, so for a minute or two one node is old
and one is new.

## Alternatives rejected

- **0.3.0 rather than 0.2.1.** Nothing in the wire protocol, the clients'
  API or the configuration changed. The dependency moved under an unchanged
  surface, and the visible difference is a bug fix. A minor bump would claim
  a feature that is not there.
- **Compare against the numbers already in `docs/performance.md`.** They are
  from an x86_64 container, and these are from an aarch64 Mac. Any difference
  would be mostly the machine. Running both versions on one machine, back to
  back, is the only comparison where the version is the variable.
- **Report the first run's clock column.** 0.17 ran second every time, under
  a load average of 11–16, and came out 3–7% slower everywhere. That is
  exactly the shape warm-up or a neighbour produces. The scan was re-run
  twice in reverse order. The gap followed the version, so it is recorded as
  a finding. Every other clock difference fell inside its own spread and is
  recorded as noise.
- **Trust that SlateDB's on-disk format is stable across a minor version.**
  It is 0.x, and both 0.16 and 0.17 change manifest handling (0.16 began
  writing ManifestV2 everywhere, and 0.17 enforces new ULID invariants on L0
  and compactions). A guess here costs the live database.

## Evidence

**The bucket, across versions.** A release `slate-serverd` built from each
version ran against one `local`-backend directory, with the explorer's own
schema. The driver is a Python script using the published client, with exact
assertions:
1. 0.16 inserted 3,000 books and read them back.
2. 0.17 opened that bucket, read the 3,000, and inserted 3,000 more.
3. 0.16 opened the bucket 0.17 had written and read all 6,000.
4. 0.17 read all 6,000.

Every read was in descending id order and checked for every id. The bucket
ended with compacted SSTs, 9 compaction records and 15 manifests from both
writers. Each server's banner named its version: `slatedb 0.16.0, foyer
0.22.3` and `slatedb 0.17.0, foyer 0.22.6`.

**Performance, from §8f:**
- **Requests:** identical in every row of all three examples. These are the
  GETs per point read, scan and query shape, and the PUTs per load chunk.
- **Loading:** unchanged, at about 48,800 rows a second.
- **Full scan:** about 7% slower on 0.17 over an in-memory store. Medians
  were 20.8–21.1 ms against 22.1–22.5 ms, in three pairs, both orders, with
  no range overlapping.
- **Point reads:** noise.

**The version guard:** `scripts/mutate.py` with the re-anchored spec, caught
by `check_versions: FAIL clients/typescript/package.json says 0.2.2;
Cargo.toml's workspace version is 0.2.1`. The record is
`ledger/mutations/20261013T205257-clients-typescript-package-json.json`.

**The new witness:** a mutation renaming §8f's heading was caught by
`check_closed_caveats: FAIL every witness is still in the tree`.

## What this does not do

**Nothing is released by this commit.** The tag follows the merge, and what
it shipped will be recorded once the registries answer, not from the run's
summary.

**The 7% is located, not explained.** No profile was taken. The guess in §8f
(new tracing spans, or filter evaluation on range scans) is labelled a guess.

**The compatibility test used a local directory, not R2.** It shows the
format crosses versions. It does not show anything specific to R2's
conditional writes, which the lease uses. Those are unchanged by this
upgrade, because the lease is this repository's code over `object_store`,
whose only change is 0.14.1 → 0.14.2.
